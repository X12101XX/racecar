# 实车适配与标定清单

检查日期：2026-10-17。适用交付：`crossfire-car-v2.run` / `crossfire-car-v2.tar.gz`。

本文按当前目标包中的实际启动链路核对，包含配置读取位置、接口缺口和现场验收方法。相对路径均从解压后的独立实车包根目录计算。**当前只有本机仿真验证，尚未连接你们的小车；所有实测记录均待填写。仿真中的尺寸、限速和制动能力不能直接作为实车标定值。**

## 1. 检查结论：哪些必须先处理

| 优先级 | 项目 | 当前实际状态 | 上车前需要完成 |
|---|---|---|---|
| 必须 | 油门与转向映射 | 网关将目标 m/s 与等效前轮转角直接交给旧驱动；旧驱动再换算 PWM。尚无经过本车验证的物理量映射 | 测量真实速度、转弯半径、中立、死区和反向序列；映射不一致时补代码适配 |
| 必须 | 车体尺寸与参考点 | 长0.42m、宽0.30m、轴距0.30m、最大等效舵角0.52rad均为仿真假设 | 实测并同步规划器与网关；确认雷达/里程计/车体使用同一参考点 |
| 必须 | 雷达、IMU、里程计坐标 | 接收数据后直接使用，不自动查 TF，也不自动消除安装偏角、位置偏移或航向零偏 | 输出符合本包坐标约定的传感器话题；单改 frame_id 或填外参字段不够 |
| 必须 | 底盘失联停车、物理急停与控制权 | 历史驱动源码有超时中立逻辑；当前车上二进制、控制器和电调行为未知 | 架空验证实际停车链路，确认没有其他程序直接控制串口/底盘 |
| 必须 | 前进、制动及倒车能力 | 运动参数和制动估计来自仿真；当前启动器在 --arm 时要求 allow_reverse=true | 按实际地面与载荷验证；不能可靠倒车时需补纯前进部署分支，不能虚填确认项 |
| 必须 | 场地与初始姿态 | 使用所选场景的尺寸、四角、起点、据点和营地 | 现场测量、保存并传给 --config-dir；保证摆车方向和 IMU 航向基准一致 |
| 按赛规验收 | 播报/显示与录像 | 实车启动器只读时 tts=none，启用输出时 tts=auto；不自动启动录像节点；ROS文字消息不等于扬声器或现场显示屏 | 确定现场可见/可听的输出方式和真车录像方案，需要时补启动配置 |
| 必须 | 开发板环境和运行时延 | 本机验证为 x86 ROS2 Humble 容器；没有当前昇腾板的运行记录 | 用板上匹配的 Python/ROS 环境构建，实测传感器时延、任务频率和规划耗时 |

前五项中，**底盘单位映射、传感器外参适配、仅压缩相机接入等可能需要代码修改，不是填写 JSON 就已支持**。当前默认动作确认项为 false，保持这个默认值，直到对应实测完成。

## 2. 先分清楚：实车到底读取哪份配置

实车启动链路是：

```text
tools/run_car.sh
  → tools/car_supervisor.py
    → preflight（只读）
    → mission_node（只读时不发布速度）
    → gateway（只有明确 --arm 且检查通过才启动底盘输出）
```

| 入口/文件 | 实际作用 | 容易混淆的地方 |
|---|---|---|
| config/vehicle_profile.json | 默认的硬件话题、domain、网关几何/限速和硬件确认项 | 即使传了 --config-dir，硬件 profile 默认仍从包根目录读取 |
| run_car.sh A --profile /绝对路径/硬件.json | 替换硬件 profile | 这里的 --profile 是硬件 JSON，不是仿真的保存名称 |
| run_car.sh A --config-dir profiles/generated/现场名 | 指定场地、robot、plan、vision、route 配置目录 | 不会把该目录内的 vehicle_profile.json 自动选为硬件 profile |
| run_ros_sim.sh --profile 现场名 | 仿真入口：编译保存的场景源 JSON | 与实车 --profile 的含义不同 |
| profiles/现场名.json | 配置界面保存的源场景 | 命令行传配置名前先点“校验并保存”；未保存草稿不会进入仿真/实车 |
| profiles/generated/现场名/ | 界面编译出的运行配置 | UI导出会重新生成该目录；直接修改这里的硬件/高级参数前应复制到单独的车端场景目录，以免再次导出覆盖 |
| ros2_ws/src/.../config、ros2_ws/install/.../config | 构建和安装生成的副本 | 常规使用修改源 config 或传 --config-dir，不直接修改 install 目录 |
| ros2_ws/src/racecar_mission/config/car.yaml | 直接 ros2 launch 时的参数文件 | run_car.sh 不加载它；只改 YAML 不能改变 supervisor 的话题映射 |

构建/运行脚本固定 source `/opt/ros/humble/setup.bash`。硬件 profile 中的 ros_distro 字段不是自动切换发行版的入口；若当前板上不是这个环境，需要单独适配和验证。

界面的“实车标定上限”来自**运行配置编辑器的那台电脑**的根目录硬件 profile，不会自动读取远处开发板的标定数据。车端应以实际选用的硬件 profile 为准。

每次任务把场景配置复制到 `runs/时间/config/`。硬件 profile 是单独读取的，`runs/时间/config/vehicle_profile.json` **不一定是本次实际使用的硬件 profile**；现场应另外保存实际 --profile 文件和 SHA256，不能只凭该副本追溯硬件限速。

## 3. 底盘与几何：测什么、填哪里

### 3.1 指令单位是最先要确认的缺口

任务内部命令是线速度 v（m/s）和偏航角速度 w（rad/s）。网关计算：

```text
等效前轮转角 delta = atan(wheelbase × w / v)
legacy_steering 输出：Twist.linear.x = v；Twist.angular.z = delta
```

保存的历史驱动再执行：

```text
throttle_pwm = 1500 + 100 × linear.x
steer_pwm    = 1500 - 970 × angular.z
```

这只证明旧源码的算式，**不能证明 linear.x=0.30 就会实际行驶0.30m/s，也不能证明 angular.z=0.52 就对应等效前轮转角0.52rad**。例如0.30只会按该算式得到1530的油门值，可能仍在电调死区，也可能与预期速度不符。

需要记录：中立值、启动死区、多个前进/倒车命令下的独立实测速度、左右转向命令对应的转弯半径、最大可用转向、回正误差、反向等待/解锁序列。速度和制动必须在地面、实际载荷与电池状态下验证；架空只能先确认方向、回中、接口和失联行为。不要仅用由命令回填的“伪里程计”证明速度正确。

如果接口不是上述物理单位，应在网关输出边界实现经过标定的速度→油门、等效轮角→舵机映射，保留零命令严格中立、正反限幅和超时停车。`output_mode=yaw_rate` 仅适用于底盘确实接收标准物理角速度的情况，不能用它猜测修复符号。

当前 Ackermann 控制路径不使用旧 `plan.control.cmd_gain_linear/cmd_gain_angular` 做最终底盘转换；改这些字段不能完成本车标定。旧 calibrate_drive 的 confirm 动作模式也不是本车的阿克曼标定流程，当前版本会拒绝其动作请求。

若另加适配节点，应同时设计最终 `/car_cmd_vel` 的控制权检测、独立超时停车和进程监管。不能只把网关 output_topic 改成中间话题：这会改变其发布者/订阅者检查对象，原本对最终底盘话题的保护不再自动成立。

### 3.2 几何和限制值必须同步

| 实测项目 | 当前假设 | 规划侧：所选配置目录中的 robot.json | 网关侧：实际硬件 profile |
|---|---:|---|---|
| 全车包络长，含保险杠和突出物 | 0.42m | geometry.length_m | body_length |
| 全车包络宽，含轮胎和传感器突出物 | 0.30m | geometry.width_m | body_width |
| 前后轮轴距 | 0.30m | geometry.wheel_base_m | wheelbase |
| 等效前轮最大转角 | 0.52rad，约29.8° | drive.max_steer_rad | max_steer |
| 允许倒车的能力 | 规划侧true，硬件侧false | drive.allow_reverse | allow_reverse |
| 每次规划的倒车总长度预算 | 0.66m | drive.max_reverse_path_m | 无对应长度字段，网关只限制速度和扫描覆盖 |

启动器对长、宽、轴距执行相等检查，**不会替你从硬件 profile 自动覆盖 robot.json**。最大舵角也要手工同步，当前启动器不做两侧相等检查。0.52rad是单轨模型的等效轮角，不是舵机自身旋转角；可用实测半径 R 与轴距 L 核对 `delta≈atan(L/R)`。

本包使用以参考点为中心的矩形包络及单轨近似。若原始 odom、雷达或实际运动学参考点在后轴，而车体中心不在后轴，不能只改车长就认为偏移已解决：需明确统一参考点，必要时补带偏置的车体包络/运动学适配，并实测转弯时四角扫掠范围。

`max_speed=0.30`、`reverse_limit=0.15` 是当前硬件 profile 的设计限值，尚非实车测量结果。速度映射完成后，还须验证真实速度确实受限；网关现有命令限幅不等于自动完成了底盘速度闭环。

## 4. 传感器与坐标：不能只改话题名

### 4.1 数据约定和现场验证

本包平面车体系约定 x向车头、y向左、z向上；左转为正偏航。场地坐标原点取实测左下角，起步朝向由 field.start.heading_deg 指定。

| 输入 | 当前默认话题/类型 | 必须核实 | 最直接的验收方法 |
|---|---|---|---|
| 雷达 | /scan，sensor_msgs/msg/LaserScan | 0角向车头，+90°向左，前后左右距离正确；发布原点和车体参考点一致 | 在前/左/后/右分别放可测距物体，核对角度与卷尺距离；转动车身后墙的位置仍正确 |
| IMU | /imu/data，sensor_msgs/msg/Imu | rad/s、左转为正；姿态有效；航向零点与场地一致，不能把地磁北直接当赛场x轴 | 静止看零偏；手动左转看符号；在已知朝向对照 yaw；记录安装旋转和航向零偏 |
| 里程计 | /odom，nav_msgs/msg/Odometry | twist.linear.x 为真实、有符号的m/s；参考点和轴向正确 | 手动前推/后推核对符号；已知距离低速行驶后对照独立测量，核对轮径/编码器比例 |
| 相机 | /usb_cam/image_raw，sensor_msgs/msg/Image | 前视、左右不镜像、图像可解码、时间/频率和分辨率符合现场要求 | 正前、左前、右前放目标，核对画面；倒车时前摄应继续朝车头 |

雷达：RosRobotIO 和网关都直接使用 ranges 与 angle_min/angle_increment，不读取 TF 变换。`robot.sensors.lidar.angle_offset_deg` 目前没有接到这两处实车处理逻辑，填它不会自动转正雷达。只改 header.frame_id 也不会旋转/平移数据。存在安装平移或转角时需实现独立的正确重投影/重采样适配，并让规划器和网关同时订阅转换后的同一话题；保留盲区和无效束，不能把缺测伪装成“空旷”。角域建议规范到[-π,π]，避免前向覆盖判定遗漏跨2π的部分。

IMU：当前直接从四元数读取 yaw，从 angular_velocity.z 读取角速度，没有安装旋转或自动开机归零。姿态四元数需接近单位长度，orientation_covariance[0]=-1 表示不可用时程序不使用绝对yaw。不要伪造恒定有效四元数通过检查；若只有角速度，需明确适配当前自检和验证漂移。初始位置来自场景，**不会自动采用 odom.pose 或已有SLAM的map定位**。

里程计：当前使用 twist 速度做积分，odom.pose位置没有接入定位。定位还依赖能被雷达看见的已测围栏墙面；反光、透光、低围栏、强遮挡和不直的墙都需要现场验证。定位增益、墙段提取和锥桶聚类有代码默认阈值，尚无完整界面参数入口，遇到长期漏检/漂移不能只调速度掩盖问题。

### 4.2 相机内参、压缩图像与无颜色模式

镜头高度、俯仰、视场角和实际分辨率应测量记录。当前默认安装为前移0.16m、离地0.18m、俯仰-12°、水平视场90°。它们主要在仿真相机/视觉模型使用，**不会自动配置真实USB相机驱动，也不会自动纠正驱动的镜像/翻转**。

需要视觉几何时核对 vision.json 的 camera.width/height/hfov_deg/pitch_deg/height_m，以及 robot.json 中相机的安装描述。当前无颜色任务不运行颜色/色块识别，不需要为灰色物料调 HSV；它也没有另一个通用视觉避障网络，主要由雷达定位与避障。仿真低分辨率画面不能证明实车相机、录制或现场展示符合赛规。

底层 RosRobotIO 支持 CompressedImage，但当前 supervisor 只把硬件 profile 的 image_topic 作为 Image 接入。若只有压缩流，需要提供已解码的原始 Image 话题，或补 image_compressed 启动映射；不能把压缩话题直接填进 image_topic。图像格式转换支持RGB/BGR、灰度和部分YUV，其他格式需驱动转换或另做适配。

### 4.3 时间、频率、扫描覆盖与算力

| 实际生效位置 | 当前值/行为 | 实车如何处理 |
|---|---|---|
| gateway command_timeout | 0.30s | 命令更新不能长期超过这个间隔；不是 plan.safety.cmd_timeout_s 的0.4s |
| gateway sensor_timeout | 0.50s | 雷达/IMU/odom均需持续新鲜，消息时间戳要有效、不能落后超过0.5s或超前超过0.15s |
| mission sensors_fresh | 接收时间小于0.5s | 没有新鲜scan、IMU或odom就输出零；图像断流不在同一停车门限中 |
| gateway 扫描有效束 | 有限有效返回至少占35%；行进侧至少10束 | 实测视野和遮挡；只有前向雷达不能作为后向覆盖已验证，inf/无返回不自动视为空旷 |
| 控制/网关周期 | 默认50Hz / 50Hz | 在开发板上看CPU负载、规划耗时与消息间隔；不能用PC仿真耗时代替 |

这些网关超时值是 Gateway 的ROS参数默认值，当前 supervisor 没有从 vehicle_profile 透传相应字段；在 JSON 中随意新增同名字段不会生效。若实测需要调整，须补参数接线、验证保护行为与实际停车距离，不能为了让车“先跑起来”直接放宽超时。

无颜色模式算法走 CPU；可选色卡模型支持 ONNX 和 Ascend ACLLite 推理入口，板端 NPU/CANN 尚未验证，详见 [视觉加速指南](07_NPU与GPU视觉加速指南.md)。更换相机分辨率、雷达束数、场地或增加程序负载后，应重新验证计算延时。板上 Python 必须与现有ROS2/rclpy二进制兼容；不能仅凭“Python≥3.10”就换用任意解释器。`requirements.txt` 是本机工具/仿真的依赖说明，不能据此在车上全局pip升级。

## 5. 场地和运动：日常可调整的配置

场地尺寸、略歪围栏四角、起点位置/朝向、据点/营地中心和大小、封锁线间距、障碍半径及已知地图，用配置界面测量填写。源文件保存在 profiles/现场名.json，导出后通过 --config-dir 指定。只勾选确实赛前测得的已知障碍；未知障碍不应为了仿真成功而预先泄露给规划器。

指定路线 A/B 在当前 Ackermann 任务中表示“所选据点→等待→所选营地”的目标顺序，穿越路径在线规划。旧 route.cross_entry/cross_exit/corridor_y 并非这一实现的强制过点约束；若现场必须穿指定门或额外中间点，需要补相应路径约束，不能只改旧字段。

运动调参使用所选 plan.json 的 ackermann 段，或界面的保守/标准/激进预设：

| 参数 | 根据什么调整 | 当前入口/限制 |
|---|---|---|
| forward_mps、corner_mps、reverse_mps | 实测可控速度与转弯稳定性 | 请求值再与硬件 profile 限速取较小值；映射仍须先校准 |
| accel_mps2 | 实际电调响应和轮胎附着 | 控制器的速度指令斜坡，不代表实车电调已按此加速度闭环 |
| brake_mps2 | 地面上测得的保守制动能力 | 允许0.1～0.6m/s²；默认0.6是假设，不能高估实际制动 |
| lookahead_m | 轴距、实际跟踪误差和速度 | 过小可能摆动，过大可能切弯，观察完整车体而非轨迹中心 |
| planning_margin_m | 安装/定位/跟踪误差及障碍外形 | 规划额外余量；网关另有固定0.06m包络余量，不由这个字段关闭 |
| arrival_m | 区域尺寸及定位误差 | 到点中心误差，还受全车能进入区域的几何限制 |
| shift_pause_s | 电调真实换向行为 | 仅是计划停车等待，不能替代某些电调需要的反向握手序列 |

制动距离可用 `d≈v×总延时+v²/(2a)` 初步核对，最后以地面实测的最坏停车距离为准。网关还会使用实际odom速度计算保护扫掠距离；错误里程计会使该保护失真。

据点停稳等待使用 `plan.mission.hold_seconds`，当前为3s；不要只改旧 route.hold_seconds。`--motion-preset` 会覆盖本次运行的运动值，开跑前核对日志和 runs/时间/config/plan.json。真实车辆首轮宜从经验证的低速值开始，仿真激进预设成功不是实车提速证明。

## 6. 失联、倒车、控制权和播报的验收

历史驱动每100ms检查一次指令是否已超500ms并发送中立。这不是“车一定在500ms内物理停止”的证明：还涉及当前运行二进制、串口、电调、车轮惯性，以及原驱动本身退出时的MCU保护。记录实际失联→中立→完全停稳的时延与距离；物理急停要独立验证。

倒车：当前 --arm 在硬件 profile 的 allow_reverse=false 时一律拒绝，即使改了 robot.drive.allow_reverse=false 也不会自动成为可启动的纯前进模式。不能可靠倒车、缺少后向测距或电调不兼容时，应保留false并补部署分支/规划验证。前进优先不等于绝不倒车；每次规划0.66m的预算也不是整个任务的倒车总长保证。

控制权：网关要求最终输出话题恰好一个订阅者（底盘驱动），发现其他输出发布者或 /teleop_cmd_vel 发布者会锁存停车。遥控节点即使不发动作，只要还创建着发布者也会触发检查。本包不会替操作者结束这些程序，也无法检查未知程序是否绕过ROS写串口。

**动作阶段不要用 `ros2 topic echo/hz` 或 rosbag 额外订阅底盘输出话题来监看**，当前“恰好一个订阅者”检查会使任务停车。可只读查看 /crossfire/gateway_state 和任务状态；`ros2 topic info --verbose` 仅查询图信息。需要录底盘原始指令时须先设计并验证相应监控支持，不能临时取消保护检查。

播报/显示：当前 car_supervisor 在只读模式传 tts=none，在 --arm 模式传 tts=auto。/crossfire/mission/announce 和终端文本不等于扬声器或显示屏；auto 也可能因缺播放器退化为文字。上车后分别检查任务中的播放器、声卡、录音与现场展示；单独 speak_test 成功不代表整个任务音频已验收。

录像：run_car.sh 不自动启动 record_node。需另行确认真车取景、实际分辨率、存储余量与录像进程；不要用仿真视频代替真车验证。录像本身也会增加开发板负载，加入后应重测延迟。

## 7. 可先执行的只读核对顺序

以下从已解压的独立实车包根目录执行。先按你们原来的方式启动传感器和底盘；这里不提供任何运动发布命令，不重启原有服务。

```bash
bash tools/build_car.sh
source /opt/ros/humble/setup.bash
printenv ROS_DISTRO
python3 -c 'import sys,platform,rclpy,numpy,cv2; print(platform.machine(),sys.version); print(numpy.__version__,cv2.__version__)'

# 该终端需要与实际硬件profile相同的 ROS_DOMAIN_ID；命令只影响当前终端
# 0是当前交付默认值，若实车不同，使用已核实的实际值
export ROS_DOMAIN_ID=0
export ROS_LOCALHOST_ONLY=1
ros2 topic list -t
ros2 topic info /scan --verbose
ros2 topic info /car_cmd_vel --verbose
ros2 topic echo /imu/data --once
ros2 topic echo /odom --once

# 换成实际导出场地目录；默认没有速度发布者
bash tools/run_car.sh A --preflight --config-dir profiles/generated/measured_example
bash tools/run_car.sh A --config-dir profiles/generated/measured_example
```

话题名不同就替换上述只读查看命令，并修改实际硬件 profile。ROS_LOCALHOST_ONLY=1要求驱动与任务在同一板上且网络命名空间可互通；远端传感器/隔离容器通信不通时，仅改domain不够，应单独设计部署接入，不在现有系统中盲改网络。

最后一个只读任务会持续运行，用Ctrl+C结束本包进程。它不创建速度发布者，也不负责停止原有导航或遥控程序。

preflight目前主要检查有消息、部分内容可解码、静止速度及场地几何；PASS **不代表**油门映射、时间戳、完整坐标、后向覆盖、物理制动、播报或控制权已经验收。其“帧数>3”等检查也不是严格的传感器频率保证。进一步只读观察传感器 hz、时间戳、frame_id 和实际图像。

顺序应为：只读与数据回放→接口适配完成→架空方向/中立/失联验证→有物理急停的地面低速验证→A/B整条路线→逐项提速。会驱动车辆的阶段由现场操作者在上述实测条件具备后执行；填true本身不等于完成验证。

代码适配应在源码侧完成、验证后重建目标包与MANIFEST。不要删除完整性清单来绕过代码校验。config/profiles数据允许按需编辑；构建会重新生成包内安装副本。恢复时只结束本包进程，保留原工作空间、驱动、网络、CANN和系统服务。
